# 한국어 기술 문서 작성 기준

이 문서는 `go-bemu`의 한국어 문서를 작성하고 검토할 때 적용하는 기준입니다.
영어 문장을 그대로 옮기기보다, 한국어 독자가 필요한 정보를 빠르게 찾고 이해할 수
있도록 내용을 다시 구성합니다.

## 기본 원칙

- 설명은 `합니다`, 상태는 `입니다`, 제한은 `지원하지 않습니다`로 씁니다.
- 한 문장에는 핵심 주장이나 동작을 하나만 담습니다.
- 한 문단에는 하나의 주제만 다룹니다. 문단이 길어지면 소제목이나 목록으로 나눕니다.
- 중요한 결론과 사용자가 해야 할 일을 먼저 설명합니다. 배경과 근거는 그 뒤에 둡니다.
- 영어판의 문장 구조를 그대로 따르지 않습니다. 기술적 의미와 출처만 같게 유지합니다.
- 표에는 비교하기 쉬운 짧은 내용만 넣습니다. 긴 제약 사항과 예외는 표 아래에서
  설명합니다.

이 기준은 국립국어원의 [쉬운 공공언어 쓰기 기본
길잡이](https://www.korean.go.kr/common/download.do?c_file_name=d1ce1113-cc07-4f4c-9ea2-dd920eecba7b.pdf&file_path=etcData)와
[Microsoft Learn 기술 콘텐츠 스타일
안내](https://learn.microsoft.com/ko-kr/contribute/content/style-quick-start)의 원칙을
참고했습니다. 두 자료 모두 짧고 자연스러운 문장, 익숙한 단어, 독자의 목적을 먼저
고려하는 구성을 권장합니다.

## 용어 선택

코드 식별자, API 이름, 설정 키, 오류 코드, 고유 기술명은 원문을 유지하고 백틱으로
표시합니다. 설명에 사용하는 일반 명사는 가능한 한 자연스러운 한국어로 씁니다.

| 피할 표현 | 권장 표현 |
| --- | --- |
| gate | 확인 절차, 판정 기준, 변경 조건, 잠금 |
| gap | 미지원 항목, 남은 차이 |
| shape | 요청 구조, 응답 구조, 데이터 구조 |
| bounded | 상한이 있는, 최대 크기가 정해진 |
| public edge | 공개 API 경계 |
| runtime | 실행 환경, 실행 시점 |
| lifecycle | 수명 주기 |
| fixture | 시험 데이터, 시험 환경 |
| runbook | 운영 절차, 작업 절차 |
| payload | 요청 본문, 응답 본문, 전송 데이터 |
| canonical metadata | 기준 메타데이터 |
| physical DDL | 저장 엔진 내부 DDL |
| publication | 메타데이터 반영, 공개 |
| fail closed | 안전하게 거부 |

실제 필드명이 `shape`이거나 안정적인 미지원 항목 식별자에 `gap`이 포함되어 있다면
원문을 바꾸지 않습니다. 처음 나올 때만 한국어 설명을 덧붙입니다.

## 지원 상태

문서 본문에서는 다음 한국어 상태를 사용합니다.

- **검증 완료:** 지정한 클라이언트와 버전으로 공개 API 동작을 확인했습니다.
- **일부 지원:** 핵심 경로는 동작하지만 문서에 적은 제약이 남아 있습니다.
- **미지원:** 요청을 실행하지 않고 명확한 오류로 거부합니다.
- **클라우드 전용:** Google Cloud의 제어 영역이 필요하므로 로컬에서 재현하지 않습니다.

JSON이나 프로그램이 읽는 상태값은 기존 영문 값을 유지합니다. 이 경우 백틱으로
표시하고 바로 옆에서 뜻을 설명합니다.

## 문장과 문단

다음과 같이 여러 동작을 한 문장에 이어 쓰지 않습니다.

> 애플리케이션은 잠금을 획득하고 테이블을 조회하며 스키마를 검사한 뒤 트랜잭션을
> 실행합니다.

동작 순서가 중요하면 문장을 나누거나 번호 목록을 사용합니다.

1. 애플리케이션이 카탈로그 변경 잠금을 획득합니다.
2. 원본 테이블과 대상 테이블의 스키마를 확인합니다.
3. 저장 엔진에서 트랜잭션을 실행합니다.

제한 사항은 결론부터 씁니다. 예를 들어 “현재는 중첩 필드 선택을 지원하지 않습니다”라고
먼저 말한 뒤, 필요한 경우 이유와 대안을 설명합니다.

## 검토 항목

문서를 제출하기 전에 다음 항목을 확인합니다.

- 문장이 존댓말 설명체로 끝나는가?
- 한 문장에 서로 다른 주장이 여러 개 들어 있지 않은가?
- 영어 명사를 나열하거나 영어 어순을 그대로 옮기지 않았는가?
- 설정 키와 코드 식별자를 백틱으로 표시했는가?
- 표의 한 셀이 지나치게 길지 않은가?
- 미지원 기능과 오류 동작을 독자가 찾기 쉽게 설명했는가?
- 영어 문서와 `doc-id`, `section` 표식, 주요 출처가 일치하는가?

마지막으로 `go test ./docs`를 실행해 문서 쌍, 절 순서, 링크와 출처를 확인합니다.
