# 저장 엔진 어댑터 구현 안내서

<!-- section: ownership -->
## 상태와 저장소의 소유권

BQEMU 상태와 저장 엔진은 서로 다른 정보를 책임집니다. BQEMU 상태 어댑터는 프로젝트,
데이터 세트, 테이블, 논리 스키마, 파티션, 클러스터링, 만료 정보와 제어 영역 기록의
기준입니다. 운영용 상태 어댑터는 SQLite이며, 컨테이너 설정에서는
`/data/bqemu-state.sqlite`에 저장합니다.

저장 엔진은 물리 스키마, 테이블, 행, 준비용 릴레이션, 스냅샷과 엔진 내부 객체만
소유합니다. 엔진 카탈로그를 BigQuery 메타데이터의 기준으로 사용하면 안 됩니다.
엔진 카탈로그에서 BigQuery 리소스를 복원하거나 엔진 자료형을 기준 스키마로 공개해서도
안 됩니다. 현재 엔진 어댑터는 DuckDB이며, 컨테이너 설정에서는
`/data/bqemu.duckdb`에 저장합니다.

```text
REST / Storage RPC
        |
  애플리케이션 유스케이스
     /             \
SQLite 상태        저장 엔진 포트
(기준 정보)        (물리 행과 객체)
```

이 구분은 공개 [BigQuery 테이블 리소스
계약](https://cloud.google.com/bigquery/docs/reference/rest/v2/tables#Table)을
따릅니다. 엔진을 바꾸더라도 리소스 식별자, 작업 상태 전환과 공개 전송 형식은 바뀌지
않아야 합니다.

현재 SQLite에는 카탈로그 리소스와 변경 기록용 기본 기능을 영속화합니다. 쿼리 및 로드
작업, Storage Read 세션, Storage Write 스트림 기록과 로드 중복 방지 기록은 아직
프로세스 안에만 있습니다. 이 정보도 BQEMU 제어 영역에 속합니다. 영속성이 필요하다는
이유로 엔진 카탈로그에 옮기면 안 됩니다.

## 포트 구성

새 어댑터는 필요한 최소 포트만 구현합니다. 드라이버 연결이나 백엔드 SQL을
애플리케이션에 노출하는 하나의 큰 인터페이스를 만들면 안 됩니다.

| 포트 | 어댑터가 맡는 동작 |
| --- | --- |
| `HealthChecker` | 엔진이 작업을 받을 수 있는지 확인합니다. 준비 상태에서는 SQLite 상태 확인과 함께 사용합니다. |
| `EngineCapabilityProvider` | 엔진 자료형 이름이나 SQL 없이 이식 가능한 제한을 보고합니다. |
| `SchemaPlanner` | 현재 전체 스키마 검사 포트입니다. 물리 변경 전에 기준 스키마를 표현할 수 있는지 검사합니다. |
| `WarehouseAdmin` | 기준 식별자로 물리 데이터 세트와 테이블 객체를 만들거나 삭제합니다. |
| `TableSchemaPlanner` | 물리 SQL을 노출하지 않고 기준 테이블의 변경 전후 계획을 만듭니다. |
| `TableSchemaMutator` | 애플리케이션이 승인한 스키마 변경 계획만 적용하고 물리 저장소가 예상 기준 스키마와 일치하는지 확인합니다. |
| `TableDataReader` | 기준 스키마 순서에 맞춰 물리 행을 페이지 단위로 읽습니다. |
| `QueryAnalyzer` | 파서 객체나 SQL이 아니라 테이블 참조와 문장 특성을 반환합니다. |
| `QueryEngine`, `QueryMaterializer` | 요청을 실행하고 물리 대상 작업 하나를 원자적으로 적용합니다. |
| `QueryOperationAnalyzer`, `QueryOperationEngine` | 버전이 정해진 커넥터 작업을 인식하고 기준 메타데이터를 받은 뒤 실행합니다. |
| Storage Read/Write 및 로드 포트 | 각 패키지 계약에 따라 스냅샷, 준비 행과 객체 로드를 처리합니다. |

`CatalogRepository`, 작업 저장소와 변경 기록은 상태 포트이며 저장 엔진 포트가
아닙니다. 상태와 엔진 사이의 호출 순서는 애플리케이션 서비스만 정합니다. 컴파일
시점의 인터페이스 확인은 필수이지만, 실제 계약은 동작 테스트로 확인해야 합니다.

## 지원 기능과 스키마 계획

지원 기능에는 최대 10진수 정밀도, 중첩 필드와 반복 필드 지원처럼 엔진과 무관하게
설명할 수 있는 사실만 담습니다. 계획기는 `CREATE TABLE`, 스키마 변경, 로드 준비 또는
쿼리 대상 DDL을 실행하기 전에 전체 기준 스키마를 검사합니다. 표현할 수 없는 필드를
문자열로 바꾸거나 펼치거나 생략해서는 안 됩니다. 요청을 명확하게 거부해야 합니다.

**현재 계약:** `EngineCapabilities`에는 최대 10진수 정밀도와 스케일, 기본 구조체와
반복 필드 지원 여부가 있습니다. `TableSchemaChanges`에는 `AddColumn`, `DropColumn`,
`RenameColumn`, `AlterColumnType`, `Transactional`, `InspectBeforeAfter`를 각각
보고합니다. `TableSchemaPlanner.PlanTableChange(before, after)`는 기준 변경 전후 테이블과
물리 지문을 담은 `TableSchemaChangePlan`을 반환합니다. SQL 원문은 넣지 않습니다.
애플리케이션은 변경 전략을 정하기 전에 이 결과를 받습니다. `TableSchemaMutator`는 계획을
적용하고, `TableSchemaMatches`는 복구 과정에서 물리 저장소와 예상 기준 스키마가
일치하는지 확인합니다. DuckDB는 최상위 스칼라 열의 네 가지 변경을 모두 지원한다고
보고하며 각 작업을 물리 트랜잭션 하나로 적용합니다. 구체 어댑터 자료형이나 백엔드가
`ALTER TABLE`을 받았다는 사실로 지원 여부를 추정하면 안 됩니다.

`SchemaPlanner.ValidateSchema`는 전체 스키마를 표현할 수 있는지 계속 검사합니다. 기준
SQLite 저장소를 사용하는 구성에서는 계획한 모든 테이블 스키마 변경을 적용 전에
기록합니다. 기준 변경 기록이 없는 상태 저장소에서는 열 추가와 이름 변경에 제한 시간을
둔 역방향 계획 보상을 사용할 수 있습니다. 해당 구성에서는 열 삭제와 자료형 변경을
거부합니다.

계획기는 기준 필드를 입력으로 받습니다. 물리 실행 계획을 만들 수 있지만 그 결과는
어댑터 안에만 둡니다. 생략된 10진수 매개변수는 SQLite 메타데이터에서도 생략된 상태로
유지합니다. 물리 계획을 만들 때만 기본값을 계산합니다. 지원할 수 없는 조합은
드라이버를 호출하기 전에 안정적인 도메인 오류로 반환합니다.

새 엔진에 필요한 정보를 기존 포트로 나타낼 수 없다면 포트와 테스트를 먼저
확장합니다. 시험용 DDL의 성공 여부로 지원 기능을 판단하는 방식은 계약으로 사용할 수
없습니다.

## 기준 자료형 정책

공통 정책에서는 Spark가 허용하는 최대 10진수 정밀도 38을 사용합니다. 따라서
[BigQuery 자료형 전체
범위](https://cloud.google.com/bigquery/docs/reference/standard-sql/data-types)보다
좁습니다.

| 기준 자료형 | 필요한 물리 동작 |
| --- | --- |
| `BOOL`/`BOOLEAN`, `INT64`/`INTEGER`, `FLOAT64`/`FLOAT` | 기본 자료형으로 변환하되 SQLite에 저장한 기준 별칭은 바꾸지 않습니다. |
| `STRING`, `BYTES`, `DATE`, `DATETIME`, `TIME`, `TIMESTAMP`, `JSON` | 엔진의 기본 표현을 사용하고 어댑터 경계에서 공개 인코딩 계약을 보존합니다. |
| `NUMERIC` | 정밀도 38 이하의 기본 10진수로 저장합니다. 매개변수를 생략하면 `(38,9)`를 사용합니다. |
| `BIGNUMERIC` | 정밀도 38 이하의 기본 10진수로 저장합니다. 매개변수를 생략하면 `(38,18)`을 사용합니다. |
| `RECORD`/`STRUCT` | 기본 구조체로 저장하며 중첩 필드 이름과 순서를 보존합니다. |
| `REPEATED` | 계획한 요소 자료형의 기본 리스트를 사용합니다. 반복 구조체도 JSON이나 문자열이 아닌 구조체 리스트로 저장합니다. |
| `GEOGRAPHY` | 지원하지 않습니다. 문자열로 저장하지 말고 기준 스키마 검사에서 거부합니다. |

DuckDB는 기본
[`STRUCT`](https://duckdb.org/docs/stable/sql/data_types/struct)와
[`LIST`](https://duckdb.org/docs/stable/sql/data_types/list)로 중첩 자료형을 처리합니다.
두 10진수 계열에는 기본
[`DECIMAL`](https://duckdb.org/docs/stable/sql/data_types/numeric)을 사용합니다. 다른
어댑터도 구현한 모든 포트에서 null 허용 여부, 반복 값, 중첩 순서, 10진수 경계와 왕복
변환을 시험해야 합니다.

## 변경 수명 주기와 원자성

엔진 트랜잭션은 해당 엔진 안에서만 원자적입니다. SQLite 트랜잭션도 BQEMU 상태 안에서만
원자적입니다. 두 파일을 묶는 분산 트랜잭션은 없습니다.

두 저장소를 함께 바꾸는 작업의 순서는 애플리케이션이 관리합니다.

1. 기준 상태, 지원 기능과 사전 조건을 확인합니다.
2. 변경 기록을 사용하는 작업이면 영속 의도를 먼저 남깁니다.
3. 물리 엔진 트랜잭션을 적용합니다.
4. 기준 SQLite 변경을 반영합니다.
5. 변경 기록을 완료 상태로 바꾸거나 별도 제한 시간을 적용한 보상 작업을 실행합니다.

생성, 삭제, 쿼리 대상 반영과 스키마 변경에는 서로 다른 적용 순서와 보상 작업이 필요할
수 있습니다. 그 순서를 어댑터가 정하면 안 됩니다. 보상 작업은 다시 실행해도 안전해야
합니다. 엔진 커밋 결과를 알 수 없을 때 성공으로 처리해서도 안 됩니다. 엔진 내부의
원자성은 [DuckDB
트랜잭션](https://duckdb.org/docs/stable/sql/statements/transactions)처럼 해당 백엔드의
문서를 따릅니다.

SQLite에는 변경 의도를 수정할 수 없도록 저장하는 원장이 있습니다. 상태는
`PREPARED`, `APPLIED`, `FAILED`로 전환하며 테이블 스키마 DDL은 이 원장을 사용합니다.
기본 프로젝트를 만들거나 수신기를 열기 전에 시작 절차가 미완료 변경을 다시 계획하고
물리 지문을 확인한 뒤 DuckDB 상태를 검사합니다. 물리 상태가 변경 후와 같으면 기준
변경을 반영하고, 변경 전과 같으면 계획을 다시 적용합니다. 어느 쪽과도 같지 않으면
시작하지 않습니다. 미완료 기록을 처리한 뒤에는 전체 데이터 세트와 테이블의 누락, 추가,
스키마 불일치도 검사합니다.

아직 모든 작업을 복구하는 것은 아닙니다. 리소스 생성과 삭제, 쿼리 대상 반영을 비롯한
다른 두 저장소 변경은 의도를 모두 기록하지 않습니다. 이러한 작업의 장애 후 복구와
재실행은 미완성이며 두 저장소를 묶는 분산 트랜잭션도 없습니다. 실행 중인 인스턴스에서는
두 파일 중 하나만 백업해서 완전한 상태를 얻을 수 없습니다.

## 중복 방지와 오류

재시도 키 하나는 변경 의도 하나만 나타냅니다. 리소스, 변경 종류, 예상 리비전과 변경
전후 물리 지문이 같은 키를 다시 사용하면 기존 기록을 반환합니다. 내용이 다르면 충돌로
처리합니다. 완료한 변경 기록은 비교 후 교체 방식으로만 전환하며 이전 상태로 되돌릴 수
없습니다.

정리 작업에 쓰는 물리 도우미는 반복 실행할 수 있어야 합니다. 예를 들어 보상 삭제는
준비 객체가 이미 없어도 안전해야 합니다. 정리 작업을 반복할 수 있다는 이유만으로 공개
생성 또는 삭제 API가 자동으로 멱등성을 갖는 것은 아닙니다.

어댑터는 `context.Canceled`와 `context.DeadlineExceeded`를 보존합니다. 입력 오류,
미지원 기능, 없는 리소스, 충돌, 오래된 사전 조건, 잘못된 쿼리와 백엔드 오류를 저장소의
도메인 오류 분류로 변환합니다. 드라이버 오류에는 처리 단계를 덧붙일 수 있지만, 드라이버
문구로 REST 또는 gRPC 상태를 정하면 안 됩니다. 커밋 결과를 알 수 없으면 성공으로
추정하지 않고 복구가 필요한 백엔드 오류로 처리합니다.

## 수명 주기와 안전한 진단 정보

공개 수신기를 열기 전에 상태 저장소를 열고 내장 마이그레이션을 확인합니다. 유스케이스를
구성하기 전에 엔진도 열어야 합니다. 준비 상태는 SQLite와 엔진을 모두 확인합니다. 종료할
때는 새 작업 승인을 막고 쿼리와 Storage 작업을 취소한 뒤 끝날 때까지 기다립니다. 이어서
엔진이 소유한 스냅샷과 조정자를 닫고 엔진과 상태 저장소를 닫습니다. 작업 종료 대기가
실패했다면 실행 중인 작업과 `Close`가 경합하도록 만들면 안 됩니다.

로그에는 안정적인 작업 이름, 모델 버전, 개수, 처리 시간, 공개해도 되는 식별자와 전체
값의 SHA-256 지문만 기록할 수 있습니다. SQL 원문, 행과 객체 내용, 인증 정보,
직렬화한 Protobuf와 드라이버 오류 원문은 기록하면 안 됩니다. 변경 실패 기록에는 안정적인
코드와 지문만 저장합니다. 공통 관측성 도우미를 사용해야 하며, 패턴에 따라 일부 문자열만
가리는 방식으로 알 수 없는 값을 안전하다고 판단하면 안 됩니다.

<!-- section: conformance -->
## 어댑터 계약 검증

새 어댑터를 실제 구성에 연결하려면 적용되는 계약을 테스트로 확인해야 합니다.

- 공개하는 모든 포트의 컴파일 시점 확인과 엔진이 아닌 시험용 구현을 사용하는
  애플리케이션 테스트가 필요합니다.
- 중첩 리스트와 구조체, 10진수 제한과 기본값, 명시적인 `GEOGRAPHY` 거부를 포함한 지원
  기능 및 스키마 계획기 테스트가 필요합니다.
- 백엔드 검색이 아닌 기준 식별자로 생성, 조회, 변경, 삭제, 결과 구체화, 준비 영역과
  롤백 동작을 확인해야 합니다.
- 상태와 엔진 사이의 각 단계에 오류를 주입해 보상 작업 재시도와 불확실한 커밋 처리를
  확인해야 합니다.
- 취소, 제한 시간, 안정적인 도메인 오류 변환과 자원 정리를 확인해야 합니다.
- 영속 상태 파일과 엔진 파일로 재시작을 시험해야 합니다. 프로세스 내부 기록은 복구할
  수 없다는 현재 제한도 문서와 일치해야 합니다.
- 중복 방지 충돌과 변경 기록의 비교 후 교체 전환을 확인해야 합니다.
- 수집한 로그에 SQL, 행, 객체 내용, 인증 정보와 오류 원문이 없는지 확인해야 합니다.

어댑터 패키지, 애플리케이션 계약, 관련 REST/gRPC 테스트와 `go test ./...`를 실행합니다.
특정 엔진 쿼리 하나가 성공했다는 사실만으로 BigQuery 전체 호환성을 주장하면 안 됩니다.
사용자에게 보이는 제한은 [호환성](compatibility.md)에 기록하고, SQL 동작은
[GoogleSQL 경계 안내서](google-sql-boundary.md)에 기록합니다.
